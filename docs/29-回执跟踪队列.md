# 钱包回执跟踪队列

2026-10-07。前端上报交易哈希后，如果交易尚未出现、尚未出块或历史状态查询暂时不可用，可以显式启动后台跟踪。服务端只调用现有回执复查流程，不签名、广播、调用模型或恢复消费许可。

## 前端调用顺序

1. 沿用 [v2](27-钱包后端v2.md) 完成审查、逐次手写声明、消费许可，再由钱包发出交易。
2. `POST /api/wallet/reviews/:id/broadcast`，提交 `{txHash}`。原同步行为及幂等规则保持不变。
3. 如观察仍不完整，`POST /api/wallet/reviews/:id/receipt/watch`，提交 `{}`，返回 202 和跟踪快照。
4. 使用 `GET /api/wallet/reviews/:id/receipt/watch` 读取进度，并用原 review／graph 接口读取实际回执、余额／allowance 与证据。
5. 停止后续查询：`POST /api/wallet/reviews/:id/receipt/watch/stop`，提交 `{}`，返回 200。恢复：`POST /api/wallet/reviews/:id/receipt/watch/resume`，提交 `{}`，返回 202。

没有调用 watch 就没有后台轮询。GET 不写库、不联网。未创建 watch 返回 404 `WALLET_RECEIPT_WATCH_NOT_FOUND`；审查不存在返回原 404。未消费许可或未上报哈希返回 409；前端不能通过 watch 提供新的哈希、RPC URL、期限、次数或其它参数。三个 POST 都只接受空对象。

watch 是独立 `wallet-receipt-watch-v1` DTO；本轮不增加字段到现有严格的 review、history、actions 响应，也不增加 actions 枚举。因此既有前端解析保持兼容。页面已有 `recheck_receipt` 时，可按此文档选择单次复查或后台跟踪；watch 本身不会重新审查交易。

## 快照和状态

`WalletReceiptWatchSchema` 从 `@verdict/protocol` 导出。

| 字段 | 含义 |
| --- | --- |
| schemaVersion / reviewId / txHash | 协议版本及绑定的审查／已上报交易 |
| status / reason | 下表中的跟踪状态和固定原因码 |
| attempts / maxAttempts | 已登记复查次数与创建时的次数上限；一次复查可能包含多次 RPC |
| createdAt / updatedAt | 创建和最近持久化时间，毫秒 |
| deadlineAt | 创建时固定的截止时间，毫秒 |
| nextPollAt / lastPollAt | 预计下次执行／上次登记复查时间，尚无或结束时为 null |
| finishedAt | 本轮跟踪结束／暂停时间，进行中为 null，resume 后清空 |

| 状态 | 含义 |
| --- | --- |
| QUEUED | 已登记，等待工作槽位 |
| RUNNING | 复查已登记，可能正在查询或加入相同哈希的在途查询 |
| WAITING | 观察仍未知或缺失，按退避时间等待下一次 |
| COMPLETED | 观察证据已保存；交易可能 SUCCESS 或 FAIL，代币事件／状态也可能不匹配 |
| REJECTED | 原回执检查已拒收不匹配的交易或回执，不再轮询 |
| EXHAUSTED | 次数或时间用尽，观察仍以 review 实际结果为准；不能据此断言交易失败 |
| STOPPED | 用户停止、重启暂停、配置关闭或任务无法继续，具体见 reason |

模型 verdict、用户风险继续、消费许可、receipt status、代币结果和 watch status 各自保留。`COMPLETED` 只说明已保存观察；不宣称交易安全、最终性或资产核对通过。后台不持续监测已经存证后的链重组；证据可通过既有独立复验接口重新检查。

## 限额、幂等与恢复

每个 review 只有一条 watch 记录。重复 start 返回同一记录，包含 STOPPED／EXHAUSTED 等终态，不重建任务。resume 只恢复 STOPPED 且仍有原始预算的任务；不延长截止时间、不清零次数。EXHAUSTED 不自动恢复；原单次 `receipt/recheck` 接口仍可由用户显式调用。

配置在 `wallet.receiptTracking`，省略时默认如下：

```json
{
  "enabled": true,
  "pollIntervalMs": 5000,
  "maxAttempts": 12,
  "maxDurationMs": 180000,
  "maxPending": 32,
  "concurrency": 1
}
```

`enabled` 只允许显式 watch，不自动为已有交易创建任务。间隔逐次为基础间隔的 1、2、4、8 倍，之后保持 8 倍，单次间隔最多 60 秒；默认截止 3 分钟，未必能用完 12 次。配置允许间隔 100–60000 ms、次数 1–100、时间 100–600000 ms、待办 1–128、工作槽位 1–2。满队列返回 429 `WALLET_RECEIPT_QUEUE_FULL`；已有任务幂等查询不重复占位。

次数在发起 RPC 前持久化，崩溃时也不会退还已登记次数。后台与手动复查共用现有的同任务请求合并和全局最多两项回执查询限制。登记前发现没有槽位则延后，不消耗新的尝试次数；已经登记的轮次即使随后遇到并发争抢，也不返还。到截止时间不再启动新查询；已经在途的复查仍受原回执流程总超时 `rpcTimeoutMs × 4` 约束，可能在截止时间之后结束。

任务保存在当前实例 SQLite，沿用单写者约束。服务重启时先用已存的 review 核对是否已经存证／拒收，不发 RPC；未完成且仍有预算的任务改为 STOPPED / `RESTART_REQUIRES_RESUME`，由前端显式 resume。已过期／耗尽改为 EXHAUSTED。已消费交易可以在钱包断开或原签名前 TTL 到期后继续观察，这不会恢复签名权限。

stop 只取消后续轮询；已经在途或与手动复查共用的 RPC 可以完成并保存真实观察，不会把 STOPPED 改回运行。此时立即 resume 返回 409 `WALLET_WATCH_STOP_IN_PROGRESS`。待在途查询结束后可再次 resume，它先检查已保存结果。
