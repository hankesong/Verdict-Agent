# 《周五付款》：当前后端与真实前端对照

2026-10-07。核实对象：`Verdict-Agent-wallet-v2` 工作树与当前 5182 预览连接的 3125 服务。故事是目标场景，不能作为已经接通的证据。用户本轮选择建设真实前端，不扩展 UI_MOCK 剧情来替代接口。

此文保留为迁移前的核实快照。STAGING 后续已新增风险继续、代币观察、查询接口、持久跟踪和 Agent 防御层，不能再用下文的后端缺项描述其当前状态；前端合入范围见 [025](decisions/025-staging-frontend-integration.md)，最新后端能力见 [024](decisions/024-agent-defense-layer.md)。

## 结论

当前可复用单笔钱包审查、逐次确认、一次性许可，以及 BOT 测试网原生币交易观察和独立复验。完整故事仍缺付款预设的可信服务端绑定、账单读取与付款 Agent 编排、批次关系、持久后台追踪和代币交易后的核对。

| 故事环节 | 当前支持 | 代码依据／边界 |
| --- | --- | --- |
| 保存供应商付款条件 | 无服务端预设接口 | `CreateWalletReviewSchema` 同时接收 intent 和 transaction。前端可保存本机预填配置，但不构成 Agent 无权更改的服务端授权边界 |
| 先绑定本次付款范围，再让 Agent 读取附件 | 未接通 | 钱包会话是 CLIENT_DECLARED，不验证账户所有权；创建审查时只核对会话的账户、链和版本。若调用方同时改写 intent 与 transaction，现有逐字段一致性检查不能恢复用户原条件 |
| 三笔付款、两条网络、Agent 准备草稿 | 未接通任务编排 | 钱包接口是单笔 review；付款附件、供应商、批次和草稿来源字段不存在。现有 PI 是只读审查器，不是账单付款执行器 |
| 地址／金额／网络／费用越界时拒绝签名 | 已有单笔检查 | `apps/server/src/wallet.ts` 的 policy、preflight、confirm、consume；只在传入 intent 可信、执行路径经过适配器时成立。当前 policy 遇到首个不符即返回，未返回完整差异表 |
| 每笔手写后钱包签名 | 已有 | v2 确认声明绑定 review、交易摘要、会话版本、nonce；后端不识别笔迹。前端继续使用 GuardedWallet 的 ALLOWED 门槛 |
| 取消异常并保留记录 | 已有单笔取消与持久记录 | SQLite 保存 review、事件和图。尚无跨付款尝试的任务关联、团队鉴权或财务共享检索接口 |
| 钱包关闭后继续查询，直到预算耗尽 | 未有持久调度 | broadcast／receipt/recheck 每次运行一次查询链；进程重启把未完成报告标为 REPORT_INTERRUPTED。GET review 只读旧状态；浏览器轮询 GET 不会重新查 RPC |
| 原生币交易、回执和历史状态核对 | 有限支持 | `networkForReceipt` 限 BOT 测试网 `0x3c8`、native_transfer；checkedTransaction 比对账户、地址、value、nonce、data 与费用参数，checkedReceipt 校验回执和区块关联 |
| 代币事件与资产核对 | 仅签名前受限预执行 | ERC-20 transfer／approve 配置范围内做代码、模拟、资产差额／allowance 检查；签名后 `TOKEN_RECEIPT_REPLAY_NOT_SUPPORTED`。当前 3125 配置仅开放 native_transfer |
| 证据保存与另一个实例重新查询 | 原生币支持 | wallet-evidence 重查交易、回执和指定区块状态，再比较规范化数据；返回 reviewAndPermit: NOT_REPLAYED，不复验用户授权或先前模型判断 |

## 本轮真实前端方向

- 付款条件与实际待签交易并列展示，地址完整可见；差异为字段呈现，放行仍由后端决定。
- 付款预设若保存于本机，应明确本机来源；提交前用户核对，独立传递保存条件与本次交易，不从修改后的草稿反推原条件。
- 保留异常、取消、重建付款各自的 review，不覆盖先前记录。
- 钱包返回哈希后区分已上报、等待结果、回执成功／失败、状态复查与证据；网页可做有限观察重试，不能声称关页后继续后台运行。
- 不为没有接口的账单上传、付款 Agent、批量签名和代币后验制作可点击的虚假成功入口。

## 后端后续最小增量

1. 独立鉴权入口管理预设与版本，绑定不可变的本次付款范围；执行 Agent 只持任务引用，不能提交覆盖原边界的 intent。
2. 付款任务／批次与尝试关系；原始材料只作为不可信数据，保存引用／摘要及提取结果，独立校验生成交易。
3. 全量字段差异、条件来源版本、确认／取消／消费记录查询，用户或团队隔离。
4. 持久化 receipt 跟踪任务：次数、截止时间、退避、幂等上报、重启恢复，以及明确 UNKNOWN 与执行失败。
5. 配置范围内 ERC-20 的交易后观察／证据／复验与更多网络覆盖；新能力经真实接口负例测试后再开放。
